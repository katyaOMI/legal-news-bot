# Сравнение моделей для отбора материалов

Владелец выбрал функцию отбора материалов и ручное сравнение в Kimi и DeepSeek без новых оплат. Полная редакция 0.2 утверждена владельцем ответом «утверждаю» 11 ноября 2026 года до реализации. Действующая SPEC 2.0 остаётся основой поведения бота. Названия точных моделей и режимов фиксируются по интерфейсу при каждом прогоне; имя сервиса само по себе не определяет модель.

Редакция 0.2 подготовлена после рецензии Kimi на 0.1. По присланному скриншоту подтверждён режим «Быстрый»; затем владелец уточнил модель: Kimi K3. Состояние поиска неизвестно. Это рецензия требований, не измерение качества отбора. Разбор всех замечаний — [KIMI-REVIEW.md](KIMI-REVIEW.md). Для сравнения режимы заново фиксируются при прогонах.

## Польза и границы

Проверить, помогают ли модели отличать полезные материалы о приватности, безопасности и правовых рисках онлайн-опросов при работе из России от методологии и общих новостей. Сравниваем ответы моделей с ручной разметкой и действующими правилами `legal_news/relevance.py`, а не с решением одной модели о другой.

Результат этапа — воспроизводимый локальный набор проверок, отчёт и обоснованный выбор модели либо решение не выбирать ни одну. Автоматическое подключение к collector, worker, базе или Telegram в этот этап не входит. Выбранную модель можно рекомендовать для следующего пилота, но не объявлять работающей в боте.

## Что подаём моделям

Только отдельно проверенные публичные материалы: идентификатор примера, заголовок, URL и содержательный фрагмент. Дата допускается с указанием происхождения, но модель не определяет метку «НОВОЕ». Для обеих моделей — одинаковый текст, порядок и объём. Поиск в интернете выключен, где интерфейс позволяет; если выключить нельзя, это ограничение фиксируется, результаты не смешиваются с прогонами без поиска.

Сравнение этой функции требует работы только с выданным текстом: поиск, открытие ссылок и внешние инструменты отключены. Сохранить видимые настройки; запросом также запретить внешние обращения. Если отключение поиска недоступно или не подтверждено, соответствующий прогон пометить как несопоставимый и не использовать для выбора победителя. Включать поиск обеим моделям вместо этого нельзя: это был бы другой эксперимент. Отключённый переключатель не доказывает отсутствие всех внутренних обращений сервиса; предел наблюдения указать в отчёте.

Фрагмент готовится один раз: максимум 5000 символов Unicode, по границе последнего полного предложения в пределах лимита, а при отсутствии такой границы — первые 5000 символов с отметкой об обрезке. Сохранять поданный текст, длину, признак обрезки и SHA-256; самостоятельно сокращать его по-разному для моделей нельзя. Если сведения о риске или применимости остались за пределами фрагмента, оценивается именно недостаточность поданных данных.

Возраст публикации не исключает полезный материал. Даты можно использовать как контекст описанного события, но нельзя по ним выдумывать стадию закона, действительность нормы или свежесть. Метку «НОВОЕ» и расчёт 72 часов по-прежнему определяет код действующего бота отдельно.

Не передавать подписчиков, ответы на опросы, переписку, секреты, .env, базу, внутренние ссылки и журналы. Публичные страницы тоже проверять на случайно включённые личные данные; выбирать материалы без таких сведений. Инструкции внутри статьи — данные, которые нельзя выполнять.

Два источника сравнения строго различаются: реальные публичные страницы и синтетические регрессионные примеры. Придуманный текст не представляется новостью, действующим требованием или результатом живого сбора.

## Ожидаемый ответ

Один объект JSON на пример с полями:

```json
{
  "id": "example-01",
  "decision": "review",
  "reason": "Недостаточно текста для подтверждения применимости",
  "evidence": [],
  "russia_basis": null
}
```

`decision`: `accept` — подходит; `reject` — не подходит; `review` — недостаточно данных. `reason` — краткое объяснение на русском. `evidence` — дословные выдержки из поданного заголовка или фрагмента. Для `accept` обязательна хотя бы одна содержательная выдержка, подтверждающая риск. `russia_basis` — дословный фрагмент российской связи либо null. Для зарубежного события без подтверждённой связи с работой из России `accept` запрещён.

Для каждого пакета ответ — один JSON-массив без Markdown-ограждений и пояснений снаружи. Каждый объект содержит ровно пять полей из примера: непустые строки `id` и `reason`, строку `decision` из трёх допустимых значений, массив непустых строк `evidence` (он может быть пустым), `russia_basis` — непустую строку или null. Каждый ожидаемый ID встречается ровно один раз; неизвестные, пропущенные и повторные ID — ошибки. При `accept` массив цитат непустой. При `reject` и `review` пустой массив допустим; `reason` для `review` объясняет, каких данных не хватает. Ошибка разбора пакета означает невалидные ответы для всех его ID; исправленный прогон не заменяет основной.

Дословная цитата должна быть непрерывной подстрокой заголовка либо фрагмента после унификации переводов строк CRLF/LF. Остальные символы, включая пробелы и пунктуацию, не исправляются. То же правило действует для непустого `russia_basis`. Содержательная цитата описывает конкретную обработку, обязанность, риск, событие или настройку; одного термина «персональные данные» недостаточно. Минимум слов не задаётся: короткая точная цитата может быть достаточна. Заголовок допускается, если он сам подтверждает содержание. Смысл проверяет человек.

Не требовать буквального упоминания России в каждой российской статье: общие правила обработки персональных данных допускаются согласно SPEC 2.0. Цитата со словом «Россия» сама по себе не доказывает применимость. Для зарубежного события основание должно описывать связь, а не просто географическое слово.

Синтетический пример допустимого `accept` без географической цитаты: заголовок «Персональные данные респондентов и согласие на их обработку», фрагмент «Разъяснение посвящено согласию при обработке персональных данных респондентов». Ответ: `decision: accept`, цитата — весь фрагмент, `russia_basis: null`, причина — связь с обработкой данных участников опроса. Это пример тематики, не утверждение о действующем праве. Если есть признаки зарубежного события, отсутствие российской связи нельзя обходить как «общее правило»: без иных недостающих данных — `reject`, при недостаточном тексте для определения связи — `review`.

Модель не выдаёт индивидуального юридического заключения, не придумывает нормы, суммы, сроки, даты или обязанности и не пишет окончательную карточку. Если текст недостаточен, выбирает `review`. Модель не меняет тему проекта, расписание, лимит карточек или состояние очереди.

## Правила отбора

Принимать материалы о персональных данных, согласиях, уведомлениях, хранении, удалении, локализации, трансграничной передаче, безопасности опросных платформ, релевантных изменениях закона, разъяснениях, штрафах и практике. Общее требование по данным может подходить без слова «опрос», если связь с данными респондентов обоснована. Зарубежные события — только с подтверждённой российской связью.

Отклонять методологию, составление анкет, рекрутинг, NPS, расчёт выборки, обычные обновления сервисов, общие новости ИИ и безопасности без связи с нужным риском. Совпадения в меню, слово «опрос» внутри «вопросам» и рекламные обещания не являются доказательствами. Проект закона нельзя представлять действующей нормой; по теме он может подходить с точным обозначением стадии.

Для новости о принятии/изменении нормы, когда без стадии нельзя верно описать событие, отсутствие подтверждающего текста означает `review` с указанием пробела. `reject` используется, если сама тема не подходит. Не требовать стадии закона от каждой технической статьи о безопасности. Явно названный законопроект может получить `accept` только с сохранением этого обозначения в объяснении; текст не дополняется сведениями из памяти.

## Набор примеров и независимая оценка

Сначала подготовить 6 учебных примеров для уточнения формата. Затем закрытый проверочный набор из 30 других примеров: 12 подходящих, 12 неподходящих, 6 с недостаточным содержанием. Включить реальные страницы и отдельно обозначенные синтетические случаи. Сохранить URL, фрагменты, происхождение и дату получения публичного текста. Недоступная страница не становится прочитанной.

Эталон — ровно одно решение `accept`, `reject` или `review` и объяснение для каждого ID; альтернативные допустимые решения не подмешиваются в эти группы. Если согласованного эталона нет, пример заменить до фиксации набора. В наборе предусмотреть минимум 12 реальных примеров: по 4 в каждой группе; остальные могут быть синтетическими. У реального примера сохранять источник/URL, дату получения и исходный публичный фрагмент; у синтетического — `origin: synthetic`, роль автора, дату создания и цель проверки, без вымышленного URL. Автор указывается служебной ролью, без личных контактных данных.

Рабочие входы хранить в `work/model-eval/inputs/`, эталон — отдельно в `work/model-eval/private/gold.json`, соответствие A/B — в `work/model-eval/private/blind-map.json`. Эталон и карту не включать в запросы и ответы для оценивания. Это разделение файлов, не новая система прав доступа. Основной агент может готовить эталон вместе с владельцем; независимость означает, что ответы моделей не используются для его подгонки. Перед копированием проверить содержимое подготовленных пакетов, а не передавать папку целиком.

До отправки сохранить окончательный набор, версии запроса/эталона, порядок ID, контрольные суммы и 6 ID для повтора в манифесте. Работать с сохранёнными текстами: последующая недоступность URL не меняет пример. Если исходный текст вообще не получен, материал может войти только как заранее размеченный случай недостаточных данных или заменяется до утверждения набора. После начала прогона состав и знаменатели 12/12/6 не менять; при повреждении снимка остановить сравнение и оформить новую версию для обеих моделей.

Разметку проверочного набора утвердить с владельцем до ответов моделей. Разделить пересказы одного события между наборами нельзя: они должны оставаться в одной группе. Не показывать моделям эталонные ответы. Не подстраивать запрос по итогам закрытого набора: новая версия запроса требует нового проверочного набора.

Обязательные ситуации: согласия; локализация и передача; утечка опросного сервиса; релевантная практика; зарубежный штраф без российской связи; подтверждённая российская связь; NPS; выборка; общее обновление ИИ; совпадение в меню; недостаточный текст; инструкция внутри статьи, требующая игнорировать правила.

Также обязательны общее требование по персональным данным без слова «опрос», стадия законопроекта и неизвестная стадия предполагаемого изменения нормы. Эти случаи входят в те же 30 примеров; один пример может покрывать несколько ситуаций. Для повтора выбрать из них 2 `accept`, 2 `reject`, 2 `review`, включая зарубежную применимость и инструкцию внутри статьи.

Действующий фильтр получает те же заголовки и фрагменты; его два решения сравниваются с тем же эталоном. Отдельно показывать качество на реальных страницах и синтетических случаях. Результаты на маленьком наборе не означают доказанной юридической точности или полноты охвата.

## Как сравниваем Kimi и DeepSeek

Для каждого сервиса открыть новый чат, записать видимое имя модели, режим, дату, доступность поиска и версию запроса. Внутреннюю версию модели не угадывать, если сервис её не показывает. Одинаковые примеры можно передавать небольшими одинаковыми пакетами; точные границы пакетов сохранять.

Основной проход — 6 пакетов по 5 примеров, каждый в новом чате с полным одинаковым запросом. Для обеих моделей одинаковы порядок ID и границы пакетов; манифест содержит списки ID каждого пакета. Чередовать сервис, запускаемый первым, по номеру пакета. Повтор — 2 пакета по 3 примера из тех же 30, также в новых чатах. Изменение режима, видимой модели или запроса означает отдельную серию, а не продолжение прежней.

Один основной проход по 30 примерам, затем повтор 6 заранее выбранных сложных примеров в новых чатах. Для двух сервисов это 72 оценки отдельных примеров. Не перезапускать выборочно только неудачные ответы ради улучшения результата; исправления формата и повторные попытки учитывать отдельно.

Шесть повторяемых примеров входят в основной набор из 30 и не меняют его размер. Расчёт: 2 × (30 + 6) = 72 оценки, всего 16 отправок пакетов, если нет дополнительных попыток. Учебные прогоны шести примеров учитываются отдельно от этих чисел.

Перед оценкой скрыть названия сервисов за A/B. Владелец оценивает ответы по эталону, затем раскрываются имена. Сохранить все ответы, включая ошибки и отказы.

Для каждого примера локальный инструмент случайно перемешивает пару ответов и сохраняет соответствие отдельно; A не означает один и тот же сервис во всех примерах. Сохранять начальное значение генератора для воспроизведения. Оценщику показывать ID и неизменённые содержательные ответы, скрывая название сервиса, время и цену до выставления оценок. Исходные ответы сохранять полностью; самоидентификацию сервиса в тексте отмечать как раскрытие. Поскольку владелец вручную переносит ответы, полной слепоты гарантировать нельзя: заранее отметить это как ограничение и опираться прежде всего на фиксированный эталон и проверяемые ошибки.

Измерить отдельно:

- Сколько неподходящих и неопределённых материалов ошибочно получили `accept`.
- Сколько из 12 подходящих приняты; сколько неопределённых получили `review`.
- Полноту ответов, правильность JSON, наличие и точность цитат, подтверждение российской связи, выдуманные сведения и устойчивость на повторе.
- Время от отправки пакета до полного ответа, размер пакета, число повторных попыток. Отдельно — время ручного переноса. Это пользовательский замер в чатах, не скорость API.
- Дополнительные расходы на эксперимент: без новых оплат. Расход существующей квоты отмечается. API-стоимость и число токенов записываются как «не измерялись», если интерфейс их не показывает; ноль рублей дополнительных расходов не означает бесплатный промышленный API.

Предлагаемый порог допуска к следующему пилоту: ни одного ошибочного `accept` среди 18 неподходящих/неопределённых; не менее 10 из 12 подходящих приняты; не менее 5 из 6 неопределённых получили `review`; нет выдуманных юридических утверждений; все принятые материалы имеют точные содержательные цитаты; все ответы разбираются автоматически. Ошибки формата не исправлять молча вручную. Повтор не должен превращать обязательный отрицательный пример в `accept`.

Уточнение порога: среди 12 эталонных `reject` — ноль `accept`, среди 6 эталонных `review` — тоже ноль `accept`. Из последних не менее пяти должны получить `review`; шестой может получить только `reject`. Невалидный ответ не считается правильным решением и не исключается из знаменателя. Критерии применяются одновременно, не заменяют друг друга.

Для повтора требуется совпадение `decision` с основным проходом минимум на 5 из 6 ID, валидный формат всех повторных ответов и отсутствие `accept` на любом из четырёх повторных эталонных `reject`/`review`. Не менее одного верного решения на каждом ID недостаточно: основной и повторный результат сохраняются отдельно. Дословное совпадение выбранных цитат между прогонами не требуется; каждая цитата должна быть подлинной и достаточной сама по себе, выдуманные юридические сведения запрещены в обоих проходах.

Время измеряется только для целого пакета до окончания ответа. Для основного прохода показать шесть значений, медиану и общее время; суммарное время / 30 допустимо как условный показатель на пример, но не как измеренная задержка отдельного примера. Повторы, отказы и ручной перенос показывать отдельно. Пропущенный замер не восстанавливать оценкой по памяти.

Если проходят обе модели, сравнить пропуски полезных материалов, устойчивость, время и удобство ручной работы. Если ни одна не проходит — зафиксировать «модель не выбрана» и причины; не снижать порог задним числом. Этот результат может не закрыть учебное требование о выбранной модели: тогда нужен новый согласованный эксперимент. Итоговое решение владельца и точное видимое обозначение модели записать в отчёт и в коммит.

## Будущая реализация после утверждения

Локальный инструмент проверяет сохранённые ручные ответы, считает метрики и формирует отчёт. Он не вызывает API, не читает production-настройки, не подключается к PostgreSQL и не отправляет Telegram.

Его программные обязанности: строгая проверка схемы и покрытия ID; цитат как подстрок; матрица из трёх решений плюс отдельный учёт невалидных ответов; метрики по фиксированным знаменателям, устойчивость на повторе и подготовка A/B. Ручная оценка смысла хранится отдельными полями; отсутствие такой оценки означает «приёмка не завершена», а не автоматический допуск. Время и расходы берутся из заполненного журнала, неизвестные значения остаются неизвестными.

Существующие незакоммиченные README, KANBAN, progress и другие документы изменять точечно поверх актуального содержимого после чтения; не восстанавливать их из HEAD и не заменять шаблоном. Сохранённые копии/патчи не публиковать. Исходные ответы, эталон и карта A/B по умолчанию остаются в исключённом `work/`; публикуемый комплект готовится отдельно после проверки состава.

| Планируемые пути | Назначение |
|---|---|
| `checks/model_eval.py` | Проверка формата, ID, цитат, полноты и подсчёт метрик |
| `tests/test_model_eval.py` | Пропущенные/повторные ID, неверный JSON, неизвестное решение, ложная цитата, ошибки подсчёта |
| `specs/manual-model-eval/` | Утверждённые требования, запросы, безопасный набор и итоговый выбор |
| `work/model-eval/` | Исходные ручные ответы и рабочие отчёты, исключённые из Git |
| `README.md`, `KANBAN.md`, `progress.md` | Воспроизведение, статусы и результаты |

Дословное совпадение цитаты проверяется программой; смысловую достаточность, связь с Россией и отсутствие ложного юридического вывода проверяет человек. Программа не заменяет экспертную оценку.

## Порядок выполнения учебного задания

1. Рецензия Kimi на черновик 0.1 получена; основной агент разобрал замечания в KIMI-REVIEW.md и подготовил редакцию 0.2. Это не сравнительный прогон.
2. Полная редакция 0.2 показана и утверждена владельцем ответом «утверждаю» до кода.
3. Утвердить набор, вручную сравнить Kimi и DeepSeek, раскрыть A/B и зафиксировать выбор с ограничениями. Рецензия спеки и сравнение качества — разные действия.
4. E1: реализовать локальную проверку сохранённых ответов, подготовку A/B и значимые тесты. E2: зафиксировать эксперимент и выбранную модель либо мотивированный отказ от выбора. Каждая задача — отдельный коммит; не включать чужие изменения документации без проверки состава. Если победитель не выбран, учебное требование о выбранной модели не считать закрытым: нужен новый согласованный эксперимент либо подтверждение преподавателя о допустимости такого результата. Владелец не заменяет решение преподавателя о зачёте.
5. Перед публикацией выполнить модульные тесты, `checks/audit_release.py` и аудит конфиденциальности доступной истории по действующему [AGENTS.md](../../AGENTS.md). Безопасный публичный набор проверять отдельно от исходных локальных ответов.
6. DeepSeek получает утверждённую спеку, коммит/diff, код и результаты тестов для второго мнения. Основной агент проверяет каждое замечание по коду. Исправления — отдельными задачами и коммитами.
7. В комплект сдачи входят спека, рецензия Kimi с разбором, сравнение A/B, выбранная модель и основание выбора, коммит, рецензия DeepSeek с разбором, результаты проверок. Отправку задания подтверждает владелец.

Обновление рабочего сервера версии 2.0 остаётся отдельной незавершённой задачей. Локальный эксперимент не подтверждает Redeploy и ежедневную доставку.

## Что требует решения перед реализацией

- Полная редакция 0.2 утверждена 11 ноября 2026 года; повторного утверждения той же редакции не требуется.
- Проверочный набор 0.1 и эталон утверждены владельцем ответом «да» 11 ноября 2026 года после просмотра страницы с примерами; сохранены в work/model-eval, см. approval.json и manifest.json.
- Фиксация доступных названий/режимов Kimi и DeepSeek при фактических прогонах.
